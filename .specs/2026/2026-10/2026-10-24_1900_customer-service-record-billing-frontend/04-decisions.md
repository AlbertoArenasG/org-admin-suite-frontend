# Decisiones

| Decisión                                                                                 | Razón y límite                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Preparar la definición y auditar contratos antes de redactar                             | Reducir premisas provisionales replicadas entre documentos. Cambios posteriores siguen permitidos, con revisión cruzada completa.                                                                                                          |
| Una spec de frontend para administración y facturación                                   | Ambos flujos consumen el mismo estado de facturación y comparten reglas de factura, pero mantienen permisos y fetching separados.                                                                                                          |
| Acción administrativa «Enviar a facturación» solo en NOT_SUBMITTED                       | Un selector de enum no comunica que se envía correo. El backend sigue admitiendo transiciones más amplias para escenarios futuros.                                                                                                         |
| Columna y filtro administrativo de tres estados                                          | El personal debe conocer el avance desde su listado. El filtro usa TableFilterDialog y sincronización URL/Zustand existente.                                                                                                               |
| Grupo visual «Facturación» con entrada «Registros de servicio a clientes»                | Deja espacio para futuros módulos. No hay permiso de grupo en API; la entrada usa BILLING_CUSTOMER_SERVICE_RECORDS/READ.                                                                                                                   |
| Tabla de facturación enfocada y filtro de dos estados                                    | Consecutivo, cliente, equipo, tipo de servicio y estado ayudan a localizar lo facturable. La API siempre restringe a SUBMITTED e INVOICED y no admite sort de columnas.                                                                    |
| Detalle de facturación sin seguimiento al proveedor ni notificaciones de ese seguimiento | El personal de facturación no necesita reglas, grupos destinatarios ni políticas. Además, sus nombres exigen capabilities ajenas a billing READ. La respuesta API permanece completa; la vista omite ese bloque y no muestra IDs técnicos. |
| Factura editable en ambos módulos                                                        | Solicitud expresa del cliente; cada contexto usa su endpoint y permiso UPDATE propios.                                                                                                                                                     |
| Guardar factura separado de «Guardar y marcar como facturado»                            | Guardar un avance o corregir una factura no cambia automáticamente el estado. El marcado explícito puede ejecutarse tras el guardado dentro de la misma intención UI.                                                                      |
| Al menos un archivo antes y después de marcar INVOICED                                   | Regla de interfaz aprobada para ambos editores; no se afirma como invariante del backend.                                                                                                                                                  |
| Marcar como facturado solo desde el detalle                                              | La fila no incluye archivos de factura y no puede verificar ni explicar ese paso.                                                                                                                                                          |
| Mostrar último estado y fecha del aviso **a facturación** en ambos detalles, sin reenvío | Es distinto de las notificaciones del seguimiento al proveedor, que no se muestran en facturación. El backend solo conserva el último intento; SENT significa aceptación por el servicio de correo, no entrega garantizada.                |
| Header compacto con cliente en administración y facturación                              | Proporciona contexto persistente; prop opcional conserva el portal sin cambios.                                                                                                                                                            |
| Redux por módulo; Zustand por tabla; React local para borradores                         | Evita mezclar permisos y peticiones remotas, preserva el patrón del repositorio.                                                                                                                                                           |
| No usar wizard ni ampliar primitives genéricas                                           | Dos acciones en el frame documental comunican mejor el resultado; ResourceFormActions, DocumentCollection y AttachmentUploadDialog ya cubren la interacción.                                                                               |
